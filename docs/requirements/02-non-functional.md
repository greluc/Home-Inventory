| REQ-NFR-003 | Writing an item: p95 < 300 ms. | M | 1 | A load test |

| REQ-NFR-006 | Rendering a label sheet with 500 codes: < 20 s, without degrading API response times. | S | 2 | A load test alongside API traffic |
| REQ-NFR-007 | Seeding a device with 100 000 items: < 5 min over Wi-Fi, < 300 MB locally. | S | 3 | A device test |
| REQ-NFR-008 | The application layer is **stateless** and horizontally scalable. | M | 1 | Two instances behind a load balancer without session affinity |
| REQ-NFR-009 | The system runs within 8 GB RAM in the `standard` profile and within 4 GB in `minimal`, **measured as the sum of memory reservations** — ≈ 5.2 GB and ≈ 3.5 GB respectively, plus 64 MB per installed plugin. The sums of *limits* (≈ 9.7 GB and ≈ 7.2 GB, plus 256 MB per plugin) deliberately over-commit, because each limit is sized for that service's own worst case and those do not coincide ([06 §6.7](../architecture/06-deployment-view.md)). The mandatory malware scanner ([ADR-0024](../adr/0024-malware-scan.md)), the egress proxy it needs ([ADR-0036](../adr/0036-scanner-egress.md)) and the `blobstore` service ([ADR-0043](../adr/0043-blobstore-as-its-own-service.md)) are included in both figures. **The figures are computed from [`deploy/services.yaml`](../../deploy/services.yaml), not estimated**, and they count no plugin — plugins are the separate per-plugin adder above. The earlier numbers mixed the two conventions: `standard`'s reservation total silently included three first-party plugins while its limit total did not, and `minimal`'s limit total sat 0.25 GB below what its own rows add up to. | M | 1 | Both profiles started and verified in CI under a steady load, with resident memory measured against the reservation sums — not against the limit sums, which the design states as over-committed |
| REQ-NFR-010 | No endpoint loads data without a bound; every collection is paginated and capped (max. 200 per page). | M | 0 | Verified across all endpoints |

## NFR-V — Availability and robustness (Q5)

| ID | Requirement | Prio | Stage | Acceptance |
|---|---|---|---|---|

| REQ-NFR-013 | Every derived store is fully rebuildable from PostgreSQL, with a documented and rehearsed procedure. | M | 1 | The rebuild performed quarterly |

| REQ-NFR-015 | Restorability of the backup is **verified automatically every week**; an unverified backup counts as non-existent. The verification restores the dump **and replays the WAL archive to a point in time** ([ADR-0045](../adr/0045-wal-archive-volume.md)). | M | 1 | The result as a metric; a failure is an immediate alert; the rehearsal recovers to a timestamp between two dumps, which is the only thing that tests `REQ-NFR-014` |
| REQ-NFR-016 | Event delivery is at-least-once; every consumer is idempotent. | M | 1 | Duplicate delivery produces no second effect |
| REQ-NFR-017 | A restart loses no acknowledged change and no outbox message. | M | 1 | A fault injection test |
| REQ-NFR-018 | Orderly shutdown: in-flight requests finish (max. 30 s), consumers deregister. | M | 1 | A rolling update without user-visible errors |

| REQ-NFR-037 | The UI is fully operable by keyboard. | S | 1 | A manual check per view |
| REQ-NFR-038 | WCAG 2.2 AA as the **goal**: contrast, focus indication, labels, reduced motion. Verified automatically, **without** a formal conformance statement. | M | 1 | `axe` blocking in CI; keyboard operation spot-checked per view |
| REQ-NFR-039 | The UI works on phone screens from 360 px wide and is operable one-handed. | M | 1 | A device test |
| REQ-NFR-074 | The **design system in `design-system/` is binding** for every user-visible surface of the web client and the apps. A surface that invents its own colours, spacing, components or interaction rules is a defect, not a variation. Deviating requires this requirement to be amended **first** and the repository owner to approve, exactly like any other load-bearing rule. | M | 1 | Review; no screen ships with values outside the token set |
| REQ-NFR-075 | **`design-system/tokens/tokens.json` is the single source.** The CSS under `design-system/tokens/` and the Compose `Theme.kt` are **generated** from it and never hand-edited; changing a value means changing the token and regenerating. | M | 1 | A CI drift check regenerates the artifacts and fails on any difference — the same mechanism as `deploy/services.yaml` |
| REQ-NFR-076 | **No literal colour, spacing, radius, duration or font value appears in component or screen code** — every one comes from a token. This is what makes REQ-NFR-074 checkable rather than a matter of review diligence. | M | 1 | The lint rules in `design-system/adherence.oxlintrc.json` run in CI; a raw hex value or a hard-coded `px` on a themed property fails the build |
| REQ-NFR-077 | Every foreground/background token pair carries its **measured contrast ratio** in the token set, for **both** themes, and meets WCAG 2.2 AA. | REQ-NFR-071 | **Phone, tablet and desktop are all first-class**, in both orientations. | REQ-NFR-040 | **Dark is the default appearance everywhere**, regardless of the operating system setting. The choice is stored per user and applied **before first paint**, so a light-preferring user never sees a dark flash. | M | 1 | A fresh installation and a first-time visitor get dark; the choice survives a reload with no flash of the wrong theme; both themes verified against AA |

| REQ-NFR-063 | A **service matrix** (`deploy/services.yaml`) is the source of truth; the Quadlet units and `compose.yaml` are generated from it and the Helm chart is validated against it. | REQ-NFR-067 | Start order is reliable: `Requires=`/`After=` with `Notify=healthy` (Quadlet) resp. `depends_on` with a health check (Compose). | M | 0 | A cold start without startup errors, repeated ten times |
