## CORE — Items, type system, locations, tags

### Items

| ID | Requirement | Prio | Stage | Acceptance |
|---|---|---|---|---|
| REQ-CORE-001 | An item is identified by a **UUIDv7** that may be generated by the client or the server. | M | 0 | Creation with a client-generated ID returns `201`; re-creating the same ID with the same content returns `200` |
| REQ-CORE-002 | An item has at least: name, description, kind (`PHYSICAL`/`DIGITAL`), type reference, quantity with unit. These are the columns `inventory.item` carries ([07 §7.3](../architecture/07-data-model.md)); everything else about an item is a **type field** (stage 1) or a **tag** ([04 `tagging`](../architecture/04-building-blocks.md)). | M | 0 | Creation without a name is rejected with `422`; the five named fields round-trip through the API with no type system present |
| REQ-CORE-003 | A **physical** item resides in exactly one location. | M | 0 | Creation without a location is rejected; enforced by a database constraint |
| REQ-CORE-004 | A **digital** item has no physical location but instead a carrier/account, licence key, expiry date and seat count. They arrive with the shipped **software licence** template (`REQ-CORE-030`); the licence key is `sensitive` and therefore sealed at rest ([ADR-0019](../adr/0019-sensitive-field-encryption.md)), and **not required** — a licence is often recorded before the key is to hand, and a required field somebody may not read is one they cannot supply. | M | 1 | `TypeTemplateIT` creates a digital item from that template with no location and asserts on the raw column that the licence key is not in it |
| REQ-CORE-005 | Items additionally carry the fields of their type version, validated against its JSON Schema. | M | 1 | An invalid attribute value → `422` with the field path |
| REQ-CORE-006 | Items can be related: `ACCESSORY_OF`, `PART_OF`, `REPLACEMENT_FOR`, `RELATED`. | S | 1 | A relation is creatable, visible from both sides, self-reference rejected |
| REQ-CORE-007 | An item can be a **bundle** containing other items without removing them from their location. An item may be in **several** bundles at once, so the containment is a directed acyclic graph rather than a second tree. | K | 1 | A bundle is creatable and its members keep the location they had; a cycle is rejected with `409` `bundle-cycle`, including one closed through a chain of bundles rather than directly |
| REQ-CORE-008 | Consumables have a quantity and a **minimum stock**; falling below it raises an event. | S | 1 | A quantity below the minimum produces `StockBelowMinimum` |
| REQ-CORE-009 | Deletion is **two-stage**: trash with restore, final removal as a separate operation. | M | 1 | A deleted item is fully restorable within the retention period |
| REQ-CORE-010 | Every change creates a **revision record**; earlier states are viewable and restorable. | M | 1 | The history shows before/after; a restore creates a new version |
| REQ-CORE-011 | Items can be changed in **bulk**: move, tag, change type, delete. One operation over a selection, its target stated once ([ADR-0063](../adr/0063-bulk-is-a-transaction-per-entry.md)). A change of type carries over the values whose key the new type declares with the same data type and drops the rest; the revision keeps what is dropped. | S | 1 | `BulkItemOperationsIT`: up to 500 entries per call, a status line per entry, and **an entry that fails does not take the others with it** — the entries either side of a missing item are still applied afterwards. Each entry carries its own `Idempotency-Key`; a failed entry does not spend it, so resending the whole selection finishes what the first attempt did not. `200` when every entry was applied, `207` when one was not |
| REQ-CORE-012 | An item can be saved as a **template** and used for new items. | K | 1 | Creating from a template adopts type, attributes and tags |
| REQ-CORE-013 | Attribute search is **transactionally exact** through `item_attr_index`, including during an OpenSearch outage. Setting `deleted_at` **removes** an item's rows from the side table in the same transaction, and restoring it rebuilds them: deletion is two-stage (`REQ-CORE-009`), so the table's `ON DELETE CASCADE` fires only on final removal and a trashed item would otherwise answer filters for the whole retention period ([ADR-0004](../adr/0004-attribute-storage-model.md), [07 §7.3](../architecture/07-data-model.md)). | M | 1 | A filter on a `searchable` attribute returns correct results without OpenSearch; an item moved to the trash **disappears from attribute filters, facet counts and reports immediately**, and reappears on restore |
| REQ-CORE-014 | Every item carries free-form notes with limited Markdown. | S | 1 | HTML in notes is stripped server-side |

### Type system

| ID | Requirement | Prio | Stage | Acceptance |
|---|---|---|---|---|
| REQ-CORE-020 | Item types are creatable and editable **in the running system**, without a release and without a restart. Editing a type in place covers its icon; its key, kind and parent are fixed, because each would reinterpret items already written against it, and what it *declares* changes through a draft version. | M | 1 | A new type with fields in ≤ 2 min without developer involvement |
| REQ-CORE-021 | A type defines fields with: key, multilingual label, data type, required, default, unit, constraints, help text, group, order. | M | 1 | Every property settable in the UI and represented in the API |
| REQ-CORE-022 | Supported data types: `text`, `multiline`, `integer`, `decimal`, `money`, `boolean`, `date`, `datetime`, `enum`, `multi-enum`, `url`, `email`, `quantity`, `reference`, `secret`, `file`. | M | 1 | An acceptance test per data type for input, storage, validation and display |
| REQ-CORE-023 | Fields are individually markable as `searchable`, `sortable`, `facetable`, `sensitive` and — since 2026-09-20 — **`expiry`**. | M | 1 | The marking takes effect on index, sorting, facets and encryption, and `expiry` on the overview of REQ-LIFE-013. Only a `date` or `datetime` may be an expiry, refused in the editor with a `422` and by a check constraint. Two combinations are **refused rather than accepted and ignored**: `sensitive` with any of searchable/sortable/facetable, and `sensitive` with `expiry` — a sealed value is never mirrored, so either would be a marking that silently does nothing and is met months later as “my field is missing”. `FieldDefinitionView.projected()` is the one rule that decides mirroring, so the four flags cannot drift apart |
| REQ-CORE-024 | Types support **inheritance**; an inheriting type may tighten fields but not loosen them. | S | 1 | Loosening is rejected with an explanatory message |
| REQ-CORE-025 | Types are **versioned**; an item references a type version. | M | 1 | A type change devalues no existing items |
| REQ-CORE-026 | A field is deprecated and hidden; the values remain. Final deletion first shows the affected set. | M | 1 | The preview states the exact number of affected items |
| REQ-CORE-027 | A **JSON Schema (draft 2020-12)** is generated per type version and served through the API. | M | 1 | A client validates offline with the same result as the server |
| REQ-CORE-028 | Per-field visibility rules are possible as a **simple condition** over another field of the same item. | S | 1 | The condition is evaluable offline; no loops, no external access |
| REQ-CORE-029 | Value lists (`enum` sources) are independent, reusable objects. | S | 1 | One value list is usable in several types |
| REQ-CORE-030 | Shipped type templates: book, tool, appliance, furniture, clothing, software licence, document, food. What each one brings is [`docs/reference/type-templates.yaml`](../reference/type-templates.yaml) — detailed rather than minimal (8–12 fields), decided 2026-09-13, because a template is a starting point a tenant prunes and a field nobody has costs more than a field nobody fills. | S | 1 | `TypeTemplateIT`: the eight are offered with their field counts; importing one produces an ordinary **published** type; a field can be added to its next draft, and nothing links it back to the file; importing the same one twice is refused rather than producing a second type of the same name |
| REQ-CORE-031 | Calculated fields with a formula language are **excluded**. | M | 1 | No formula language in the API; see [ADR-0020](../adr/0020-configuration-as-data.md) |
| REQ-CORE-032 | Field types that carry a unit alongside a number — `money` (ISO 4217 code) and `quantity` (unit) — project that unit into `item_attr_index.unit_value`. Any aggregation over such a field **groups by the unit**; a mixed-unit total is never produced. | M | 1 | A test with two currencies returns two rows, not one sum; the same for two units |

### Locations

| ID | Requirement | Prio | Stage | Acceptance |
|---|---|---|---|---|
| REQ-CORE-040 | Locations form an **arbitrarily deep tree** (default ceiling 12 levels). | M | 0 | Building → room → shelf → box → compartment is creatable |
| REQ-CORE-041 | Locations have **categories with their own fields**, configurable in the running system. | M | 1 | A "moving box" category with target room, packing date and seal number is creatable |
| REQ-CORE-042 | Shipped categories: building, floor, room, furniture, shelf, compartment, drawer, box, moving box, vehicle, warehouse, outdoor storage, locker. They are seeded **nameless** and translated from their keys in the client; a tenant may give any of them a name of its own, which then wins. | S | 1 | All thirteen present; each one's name, icon and mobility changeable through `PUT /catalog/location-categories/{id}`, the tenant's name reaching the picker a client builds a location with |
| REQ-CORE-043 | A category can be marked **mobile**; a mobile location is moved as a whole without moving its contents individually. | M | 1 | Moving a box with 200 items produces **one** event, not 200 |
| REQ-CORE-044 | A location's full path is retrievable without recursion. | M | 0 | `ltree` path; subtree queries served by an index |
| REQ-CORE-045 | Cycles in the tree are impossible. | M | 0 | Moving a node under its own child is rejected with `409` `invalid-move` |
| REQ-CORE-064 | **Names are unique among siblings**, case-insensitively, so that the tree a person reads is the tree the database holds. A deleted location leaves a tombstone and a tombstone does **not** block re-using its name. Written down 2026-09-12: the partial unique index `location_sibling_name` had enforced this since the first migration and no requirement stated it, so the API answered `500` for the case the schema was deliberately built to refuse. | M | 0 | Two siblings with the same name, and with names differing only in case, are both refused with `409` `name-taken`; the name of a deleted sibling is re-usable; a rename to a location's own name in different case succeeds |
| REQ-CORE-046 | A non-empty location is not deleted; it is emptied or archived. | M | 1 | The delete attempt states **the number** of contained items — “it still contains 3 items” and not “it still contains items”, because the first tells somebody what they are in for and the second sends them looking. A place holding other places is refused separately, since the two lead to different next actions. The count comes through `ItemLocationUsage`, the inverted port `inventory` publishes, because no block reads another's schema (REQ-NFR-021). `LocationTreeIT` holds both refusals. *The message said only that items were there until 2026-09-20.*<br>**Archiving a location is not implemented**: nothing in this catalogue says what an archived location does — whether it still holds things, whether it is findable — and an `ARCHIVED` state nothing can reach would be a worse answer than none |
| REQ-CORE-047 | A category may restrict its permitted child categories (optional). **No rule means everything is permitted**, so the restriction can be switched on in a tenant whose tree already exists, and withdrawing it is sending the empty set. | K | 1 | The rule is settable through `/catalog/location-categories/{id}/child-categories` and effective: a move the rule does not name is refused with `409` `invalid-move`, and goes through once the rule names it |
| REQ-CORE-048 | A location is **sealable** (a moving box); changing its contents requires unsealing. | S | 2 | A sealed box rejects content changes with an explanatory message |
| REQ-CORE-049 | The items contained in a location are listable — either directly or including the subtree. | M | 0 | Both modes return correct counts |
| REQ-CORE-050 | Locations carry photos and attachments like items. | S | 1 | A photo of a room can be attached |

## MED — Media and attachments

| ID | Requirement | Prio | Stage | Acceptance |
|---|---|---|---|---|
| REQ-MED-001 | Photos and documents can be attached to items and locations. | M | 0 | Upload and display work |
| REQ-MED-002 | An item has a **primary image** shown in lists. | M | 0 | The primary image is selectable; the first image is the default |
| REQ-MED-003 | Permitted **upload** formats: JPEG, PNG, WebP, AVIF, PDF, TXT, CSV. HEIC is **accepted and transcoded on ingest**; it is never stored in its original form. **Every image is stored as AVIF** — not only HEIC — because one stored format is one decoder path and one metadata convention ([ADR-0052](../adr/0052-one-stored-image-format.md)). Documents are stored as they arrived. **SVG is rejected.** | M | 0 | Uploading an SVG file is rejected; an uploaded HEIC file is retrievable only as AVIF; no stored blob has a HEIC magic number |
| REQ-MED-004 | The type is detected from **magic bytes**; the extension and the reported MIME type are discarded. | M | 0 | A renamed executable is rejected |
| REQ-MED-005 | Images are **re-encoded** server-side; the derivatives `thumb` (200 px), `preview` (1024 px) and `full` (re-encoded, max 4096 px) are generated **asynchronously in the `worker`** ([04 §4.1](../architecture/04-building-blocks.md)) over the broker that [ADR-0051](../adr/0051-broker-in-stage-0.md) moved to this stage for exactly this reason. | M | 0 | All three derivatives exist once the pipeline completes, and a variant URL is offered only for a variant that exists — the same rule `REQ-MED-013` applies to the bytes themselves. It read *“present after upload”* until 2026-09-11, which named a moment asynchronous generation cannot promise and which stage 0 had **no mechanism** to reach at all: `api` and `worker` are separate processes and the broker was filed under stage 1 |
| REQ-MED-006 | **EXIF data including GPS is stripped.** Retention only on an explicit tenant setting. | M | 0 | A reference image contains no coordinates after upload |
| REQ-MED-007 | Blobs are **content-addressed within a tenant** (`sha256/<tenantId>/<hash>`); a tenant's duplicates are stored once. Deduplication **never** spans tenants ([ADR-0032](../adr/0032-per-tenant-blob-addressing.md)). | M | 0 | `BlobStoreContractIT` holds both halves against the real service: a second store of the same bytes by the same tenant answers "already there", and the same bytes from a second tenant are an independent object — `exists` is false for it, which is what stops "do you have this file" being answerable across the boundary and stops the second tenant inheriting the first one's malware verdict. So: a second upload of the same file by the same tenant consumes no additional storage, and the same file uploaded by a **second** tenant produces an independent object, scanned in its own right, revealing nothing about the first tenant holding it |
| REQ-MED-008 | Uploads are **resumable** (tus) and survive network changes. | M | 1 | An interrupted upload is continued, not restarted |
| REQ-MED-009 | Storage is replaceable through the `BlobStore` port. `filesystem` is an **in-core** adapter writing to the in-deployment **`blobstore` service**, which holds the `blobdata` volume so that `api` and `worker` stay stateless (`REQ-NFR-008`) and the default media store has a backup row at all ([ADR-0043](../adr/0043-blobstore-as-its-own-service.md)), speaks gRPC over mTLS and is written in Rust because that volume-holding service is budgeted at 128 MB ([ADR-0050](../adr/0050-blobstore-service-in-rust.md)); S3 and **Nextcloud (WebDAV)** ship as **first-party plugins**, because they open a connection outside the deployment ([ADR-0026](../adr/0026-core-outbound-via-plugins.md)). | M | 1 | All of them pass the same adapter test suite, in-core and plugin alike; a network test shows the core itself reaching neither S3 nor Nextcloud; a `minimal` stack stores a photo, is restarted, and still serves it — the case that had no storage location at all before 2026-09-11 |
| REQ-MED-010 | Media is served only through **signed, short-lived URLs**, from a dedicated hostname. The signature uses `HOMEINV_URL_SIGNING_KEY_FILE` (`REQ-SEC-106`), which is not the JWT signing key. | M | 0 | Direct access without a signature is rejected; an expired or foreign signature is rejected; a URL signed with the JWT key is rejected |
| REQ-MED-011 | A blob is removed only when no link remains — with a grace period. | M | 1 | Reference counting verified; the cleanup run removes only orphans. `media_object.ref_count` is carried rather than counted, and **when it reached zero is its own column** — `updated_at` moves when a scan finishes or a derivative is recorded, so a grace period measured from it would be measured from the wrong thing. The two must agree: a check constraint refuses a row where one says unreferenced and the other does not. The **grace period is the point** (7 days, `HOMEINV_BLOB_GRACE_DAYS`): moving a photograph between items is a detach and an attach, and a sweep without one deletes the picture somebody is in the middle of moving — which deduplication makes worse, since that blob may be the one copy several items share. The weekly run of 13 §13.8 deletes the **bytes first and the row only if that succeeded**, because a row without its blob is a photograph that 404s for ever while bytes without a row are reclaimed by the next run. `OrphanedBlobSweepIT`. *Until 2026-09-20 the run did not exist at all, while a comment in `MediaErasure` said it “already removes” unreferenced blobs.* |
| REQ-MED-012 | Photos can be taken offline and are uploaded later. | M | 3 | Capture in flight mode, upload after the network returns |
| REQ-MED-013 | **Every** upload is scanned for malware before release, **in the `worker`** ([ADR-0054](../adr/0054-the-scan-is-asynchronous.md)). The upload is answered `202` with a `Location`; until the verdict arrives the blob is `PENDING_SCAN`, carries no signed URL and is not retrievable. | M | 0 | No retrieval before the scan completes — proven on the serving path and not only by withholding the URL; see REQ-SEC-091 ff. |

## SRCH — Search

| ID | Requirement | Prio | Stage | Acceptance |
|---|---|---|---|---|
| REQ-SRCH-001 | Full-text search across **name, description and notes** — the fields the `item` row carries, indexed by its **two** generated columns `search_vector_de` (`german`) and `search_vector_en` (`english`), queried by the principal's display language and `OR`-combined with the other ([ADR-0047](../adr/0047-bilingual-search-vectors.md), [07 §7.3](../architecture/07-data-model.md)). | M | 0 | Hits in all three, with PostgreSQL alone and no OpenSearch — **and stemmed**: searching *Bohrmaschinen* finds an item named *Bohrmaschine*, and *drills* finds *drill*. The column used to be a single `simple` vector, which does no stemming at all, so this requirement was satisfiable by a substring match. `notes` was added to the vectors on 2026-09-14 (`V45`): the field arrived at stage 1 with REQ-CORE-014 and nothing widened them, so it was searchable by nothing |
| REQ-SRCH-011 | Full-text search additionally covers **notes, attribute values, tags and the location path**, each from the stage at which that field exists. Served by OpenSearch, and in the `minimal` profile and during an OpenSearch outage by the `item` row, `item_attr_index` and the location `ltree` path — with the same two language configurations as `REQ-SRCH-001` ([ADR-0047](../adr/0047-bilingual-search-vectors.md)). | M | 1 | Hits in all four, in **both** adapters, stemmed in both (2026-09-14). OpenSearch holds one document per item carrying all six fields with `german` and `english` sub-fields, assembled by an indexer in `search` from three blocks' ports and kept current by the item and tag events. PostgreSQL joins four sources with `or`: the generated vector, an `exists` over `item_attr_index`, and item ids and location ids that `tagging` and `locations` matched — which is not a wider vector because a generated column reads only its own row, and a tag and a place are other blocks' rows. `OpenSearchEngineIT` and `WideFullTextIT` each assert one nonsense word per field, so a failure says which field went missing |

| REQ-SRCH-002 | Facets over type, category, tag, location subtree and `facetable` fields, **and filters over the same dimensions** — a facet you can see and cannot filter by is a count with nothing behind it. A facet is counted **without its own filter** and with every other one, because a sidebar exists to show where one could click next; `location` is the exception, keeping its filter to set the level, because a tree is drilled into by descending. `category` is the type above the type (`item_type.parent_id`), and `condition` is a **tag group** rather than a dimension of its own — both settled with the owner 2026-09-14, having been listed here without either being defined anywhere. | M | 1 | Facet counts agree with the results **for a dimension nobody filtered by**, and deliberately not for one somebody did — that is what makes the sidebar usable. Three of the five dimensions belong to other building blocks and each is resolved through that block's published port: `catalog` maps a type version to its type and its parent, `tagging` counts tags over items it is handed, `locations` rolls counts up its own `ltree`, so a facet crosses no schema boundary (ADR-0002). Counts come from `item` and `item_attr_index`, written in the same transaction as the item, so a trashed item leaves the counts immediately (REQ-CORE-013). `ItemFacetIT` holds the drill-down rule in both directions, the tree exception, that an empty result still has a sidebar, and that a dimension no type marks `facetable` is refused rather than left out |
| REQ-SRCH-003 | Filters over any `searchable` field, including range filters. Repeatable and conjunctive: `filter=attr.<key>:<op>:<value>`, with `eq`, `in`, `gt`, `gte`, `lt` and `lte`. A **range over a dimensioned field names its unit** and is refused without one, and a unit on an undimensioned field is refused too (decided 2026-09-14). | M | 1 | `filter=attr.purchasePrice:gte:100:EUR` returns correct results, and does **not** return an item priced 150 USD — which is the assertion the requirement is really about, because the wrong answer looks right. Each filter is an `exists` over `item_attr_index` and not a join, so two filters over two attributes of one item cannot return it twice; the value is compared in the column its storage class owns, cast to that type, so `90 > 100` is false rather than true. `ItemFilteringIT` holds this, the four refusals, and that a cursor is bound to the filters it was taken from |
| REQ-SRCH-004 | Sorting over `sortable` fields, ascending and descending. **One key**, with `(created_at, id)` beneath it as the tie-break; several are refused rather than reduced to the first. Rows without the value come last whichever direction is asked for, and a dimensioned field orders by its unit before its amount (decided 2026-09-14). | M | 1 | Sorting is index-backed: a plain field reads `iai_num`/`iai_text`/`iai_date`, and a money or quantity field reads `iai_unit (tenant_id, field_key, unit_value, num_value)`, which is ordered the same way. `ItemSortingIT` pages two at a time through an odd number of rows, because an ordering is easy to eyeball on one page and the bug lives at the boundary; it also holds the refusals and that a cursor is bound to the order it was taken from |
| REQ-SRCH-005 | Search is replaceable through the `SearchIndex` port; OpenSearch and PostgreSQL ship with the product. | M | 1 | A profile switch without a code change: `HOMEINV_SEARCH_ENGINE` is `postgresql` or `opensearch`, and `minimal` — which never gets OpenSearch — leaves it unset. A switch and not a probe, because "use it if it answers" erases the difference between an installation running without an index and one whose index is down; a half-configured `opensearch` aborts startup rather than quietly answering from the other engine (`SearchEngineSwitchTest`). Both adapters exist since 2026-09-14. The index is kept up to date by the seven lifecycle events `inventory` publishes plus `tagging`'s two, through the outbox and the broker, consumed in the `worker` — so a write never waits for an index and a broker outage makes it stale rather than making the inventory refuse writes. The cursor is exchanged as a *position* rather than a signed string, so the signing stays in one place and no adapter can mint a cursor nobody verified (REQ-SEC-106) |
| REQ-SRCH-006 | On an OpenSearch outage, search falls back to PostgreSQL and **says so** — through `meta.degraded: true` with `degradedReason: "search-fallback"` in the response envelope, **not** through the `Warning` header, which RFC 9111 §5.5 obsoleted in 2022 ([ADR-0039](../adr/0039-degraded-response-signalling.md)). | M | 1 | The response carries the two `meta` fields and status `200`. The service asks the configured engine whether it is available and falls back when it is not, and again when it fails <i>between</i> that question and the query — a failure opens a circuit for thirty seconds rather than being retried per request, because a search that waits for a timeout is slower than the fallback it is refusing to use. An installation that never asked for OpenSearch is **not** degraded; it is small, which is why the choice is read from the configuration and not from whether OpenSearch answers. The UI shows the state |
| REQ-SRCH-007 | Hits are always re-loaded from PostgreSQL; the index supplies IDs only. **Both** shipped adapters obey it, not only OpenSearch (decided 2026-09-14): two engines behind one port are interchangeable only if they answer the same question, and the PostgreSQL path pays one extra lookup by primary key for that. | M | 1 | A tampered index entry changes no displayed content. `SearchAndCursorIT` holds the contract: the port answers with ids, the rows are loaded through the ordinary read — so row-level security and field visibility apply — the engine's order survives, and an id the tenant cannot see shortens the page rather than failing it |
| REQ-SRCH-008 | **Saved searches** are nameable and usable as smart lists. The tenant's, not the person's: 03 §3.4 lists one beside a type and a label template as configuration, and a print run or a stocktake started from one has to be startable by somebody other than its author (decided 2026-09-14). Writing one is a member's capability, deleting one an administrator's. | M | 1 | Usable as a source for label printing and stocktakes. At `/api/v1/saved-searches` (08 §8.1), storing the query as the wire spells it — `q`, the `filter` parameters verbatim, `sort` — so a client shows one by putting it back in the query bar. Running one replays those through the ordinary search, so a smart list is the list the same query typed by hand produces: the same cursor, facets and `meta.degraded`, and never a cached set. A filter that cannot be parsed is refused when it is **saved**, by the person who can still fix it. Removal is outright with a revision recorded, because nothing points at a saved search. `SavedSearchIT` holds that an item created after the search appears in it |
| REQ-SRCH-009 | Pagination exclusively by **cursor**, never by offset. | M | 0 | A cursor with changed filters is rejected |
| REQ-SRCH-010 | A local search (prefix and substring) is available offline. | S | 3 | Search in flight mode returns results from the local store |

> **Why this is two rows and not one.** `REQ-SRCH-001` demanded full text across name, description, notes, attribute values, tags and location path at **stage 0**, priority **M**. The only stage-0 mechanism is the generated vector on the `item` row — since [ADR-0047](../adr/0047-bilingual-search-vectors.md) two of them, `search_vector_de` and `search_vector_en` — which covers name and description; notes are a stage-1 field (`REQ-CORE-014`), attribute values need `item_attr_index` (stage 1), and there is no OpenSearch before stage 1 at all. Four of the six field groups had no mechanism at the stage that required them — and `minimal` never gets OpenSearch, so for that profile the gap was permanent. Split on 2026-09-11: stage 0 promises what PostgreSQL alone delivers, stage 1 promises the rest **in both adapters**, which is the part that keeps `minimal` honest.

| REQ-LIFE-003 | A **maintenance log** per item with date, kind, cost, note, attachment. | S | 1 | `MaintenanceLogIT`. Measured from the **last maintenance entry** rather than from a fixed calendar, so servicing something early moves the next reminder instead of leaving it where it was; a thing never serviced counts from its purchase date, and from the day its record was created when even that is unknown — something has to be the start, and treating it as never due would exclude exactly the items somebody set an interval for. `ReminderRuleIT` holds the interval from the last service, the move after a second service, and that no interval means no reminder |
| REQ-LIFE-005 | **Lending**: borrower (internal or free text), handed-out date, due date, return. | S | 1 | A lent item is recognisable as such and not deletable. `inventory.loan` holds one row per handover with the return written into it, and **at most one open loan per item** by a partial unique index — so “is it lent” has one answer and not a flag beside it (07 §7.8). | REQ-LIFE-006 | Overdue returns raise reminders. | S | 1 | The `LOAN_DUE` trigger of REQ-NOTI-003, with a **negative** offset: -1 fires the day after it was due, 0 on the day itself. Who hears it is REQ-NOTI-006's answer and not the rule's — everyone subscribed to the kind on that channel, which is how it reaches the lender and the owner without the rule naming either. A loan lent with **no agreed date is never overdue**: there is nothing for it to be late against, and treating “no date” as “due now” would make a reminder out of a lend nobody put a date on. `ReminderRuleIT` holds both |
| REQ-LIFE-007 | Sale and disposal are recorded (price, date, recipient) and change the state. | S | 1 | The state change appears in the audit log. `POST /api/v1/items/{id}/disposal` and **not** a `DELETE`, which is the whole point: the item stays and stays readable, because “what did we have and what became of it” is the question an inventory answers and a `DELETE` answers half of it. It takes `ITEM_UPDATE` for the same reason — nothing is removed — and `If-Match` like every write on a single resource. Price, date and recipient are **columns** (07 §7.8): a thing is sold once, so the sequence that makes a maintenance log a table does not exist here. Only a **sale** carries a price, and a giveaway carries none rather than 0.00. **Terminal**: unlike a trashing there is no way back, since what is gone is the thing and not the record — a second disposal, and lending something sold, both answer `409 item-state`, which is its own token because “somebody has it” and “you sold it in March” lead a caller somewhere different. `ItemDisposalIT` holds the sale, the giveaway, the priced non-sale, the second disposal and the sold-then-lent refusal |
| REQ-LIFE-008 | Reporting: total value per location, type and tag — **per currency**, never mixed. | M | 1 | `GET /api/v1/reports/valuation?by=location|type|tag`. A type or a tag has no tree and the two are equal. **Tag rows overlap** — a thing carries several tags — so the answer carries `overlapping: true` rather than leaving somebody to discover it by adding the column up. Things that are sold, disposed of or in the trash are not counted: a house valued including the bicycle sold in March is wrong in a way nobody can see. `ValuationReportIT` |
| REQ-LIFE-009 | **Current value** through the `ValuationProvider` port; straight-line depreciation over a type-dependent useful life ships with the product, overridable per item. | S | 1 | The current value is computable and manually correctable — **met**. `DepreciationRefresh` writes purchase price × the fraction of the useful life still to run, nightly, and zero once that life is over. The useful life is `useful_life_months` on the **type**, settable at `PUT /api/v1/item-types/{id}`, and **no shipped type carries one** (decided with the owner 2026-09-20): how long a household's furniture lasts is a judgement about that household, and a figure this application invented would end up in somebody's insurance report. So an instance nobody has configured depreciates nothing, which is the honest state rather than a default in disguise. `current_source` is what makes the run safe to repeat — `MANUAL`, `DEPRECIATION` or `PLUGIN`, and only its own is ever rewritten, so a figure somebody typed survives the night. The source follows the **number**: a client that reads an item and writes the whole thing back sends the depreciated figure it was given, and treating that as a person typing it would freeze the value for ever. `DepreciationIT` holds all five |
| REQ-LIFE-010 | **Stocktake mode**: the expected list for a location, matching by scan, a discrepancy report. | M | 2 | The report names missing, unexpected and moved items |
| REQ-LIFE-011 | The stocktake report proposes corrections; nothing is applied automatically. | M | 2 | Every correction is individually confirmable |
| REQ-LIFE-012 | **Moving mode**: create and label a box, scan items into it, seal it, move it as a whole. | M | 2 | The full flow as an acceptance test |
| REQ-LIFE-013 | Expiry dates (warranty, licence, best-before) are collected in one overview. | S | 1 | `GET /api/v1/reports/expiries`, sorted by due date. Which attributes count is decided by a **field flag**, `expiry` (decided with the owner 2026-09-20) — because 07 §7.13 already wrote down why a report over attributes cannot work from known keys: “a report across every type cannot read a field that exists only where a type happened to declare it, under whatever name it chose”, so a tenant type calling its date `validUntil` would vanish silently. What has already run out is included by default — it is the thing somebody most wants to know about. `ExpiryOverviewIT` holds all five. *The same flag drives REQ-NOTI-003's `LICENCE_EXPIRY` reminder since 2026-09-20, which is what the flag turned out to be worth: one mark on a field, and the date is both in the overview and watched.* |

Nothing in the schema or the code derives one from another |
| REQ-LIFE-015 | Reports state purchase price, current value and replacement value **separately and unambiguously labelled** — per location, type and tag.
