# 03 — Security and Privacy

Security is quality goal **Q1** and takes precedence in every conflict of goals.
Basis: [12 Security](../architecture/12-security.md).

Unless noted otherwise, the requirements in this chapter are **priority M** —
they are not negotiable, and no stage counts as finished while those that apply
to it are open.

---

|---|---|---|---|

| REQ-SEC-004 | The tenant context is set per transaction through `SET LOCAL` from the authenticated context — **never** from a request parameter. | 0 | Code review and a test |

| REQ-SEC-006 | No connection returns to the pool with the tenant context still set. | 0 | A test across the pool |
| REQ-SEC-007 | An automated **isolation proof** checks every table with two tenants and a wrongly set context. | 0 | Part of every CI run |
| REQ-SEC-008 | Cross-tenant administration goes through explicit, logged `SECURITY DEFINER` functions with their own permission check. | 0 | The list of such functions is documented |

## SEC-B — Authentication

| ID | Requirement | Stage | Acceptance |
|---|---|---|---|
| REQ-SEC-010 | Passwords are hashed with **Argon2id** (≥ 19 MiB, t=2, p=1; raisable by configuration). | 0 | Parameters verified; upgraded on login |
| REQ-SEC-011 | Minimum length 12, no forced complexity, no forced rotation, checked against known breached passwords. | 1 | A known breached password is rejected |
| REQ-SEC-012 | Rate limiting on login attempts **per account and per IP**, with increasing delay. | 0 | A load test |
| REQ-SEC-013 | Comparison runs in constant time; for unknown accounts a dummy hash is computed. | 0 | Timing measurement shows no exploitable difference |
| REQ-SEC-110 | **An identifier that names a principal is answered identically whether or not it names anything.** An e-mail address at the login, a service-account token, a member of a tenant: the answer says the attempt failed and never which half of it failed. REQ-SEC-013 closes the *timing* channel of this same question; this closes the *content* one, and neither is enough alone. Where a count has to be given at all — how many members still lack a second factor — it is a count and never a list of names. | 0 | `EnumerationIT`: an unknown address and a known address with the wrong password answer with documents that differ only in `traceId`, and a second attempt does not diverge from the first. `ServiceAccountIT`: a revoked token and an expired one each answer the same document as one nobody issued |
| REQ-SEC-014 | Second factor through TOTP and WebAuthn/passkeys; recovery codes single-use and stored hashed. | 1 | Both verified |
| REQ-SEC-015 | The second factor is mandatory for `OWNER` and `ADMIN`, **and for any principal holding a role that may read `sensitive` fields** — whatever that role is called. Without that rule `REQ-SEC-021` is unsatisfiable for a `MEMBER`: it demands the second factor again before a licence key is shown, to an account that was never required to have one. | 1 | Assigning either role without a second factor is rejected; granting a `sensitive` field-visibility permission to a role whose members lack one is rejected with a message naming the reason |
| REQ-SEC-016 | Access tokens ≤ 10 min; refresh tokens rotating; detected reuse terminates all sessions. | 1 | A reuse-detection test |
| REQ-SEC-017 | Web sessions through a `__Host-` cookie with `Secure`, `HttpOnly`, `SameSite=Strict`, plus a CSRF token for state-changing calls. | 0 | Cookie attributes verified |
| REQ-SEC-094 | Code resolution uses a **second** cookie: `__Secure-` prefixed, `Path=/c`, `SameSite=Lax`, `Secure`, `HttpOnly`, referencing the same server-side session and granting **no** authority of its own. It is created and destroyed with the session and is revoked by remote sign-out. Its sole effect is that `GET /c/{code}` recognises a signed-in user arriving by cross-site navigation ([ADR-0029](../adr/0029-session-cookie-and-oidc-state.md)). | 2 | The cookie is rejected on any path other than `/c`; presenting it alone to any other endpoint yields `401`; remote sign-out invalidates it; a scan from a foreign camera app reaches the item without a login round trip |
| REQ-SEC-095 | The OIDC `state` and the PKCE verifier are stored **server-side**, keyed by a single-use handle carried in `state`. They are never placed in a cookie. | 1 | A replayed callback is rejected; the verifier appears in no cookie and in no log |
| REQ-SEC-018 | Password reset: a single-use token, valid 30 min, terminates all sessions, notifies the old address. | 1 | The flow verified |
| REQ-SEC-019 | Apps authenticate through OAuth 2.1 (code + PKCE) in the system browser; **no password in the app**. | 3 | The flow verified |
| REQ-SEC-020 | No automatic linking of an OIDC account to an existing one by e-mail address alone. | 1 | Linking requires re-authentication |
| REQ-SEC-021 | Critical operations require re-confirmation of the second factor. Every principal who can reach one of those operations therefore has a second factor by `REQ-SEC-015` — the two are one rule read from opposite ends. | 1 | The list of operations documented and tested; no operation on it is reachable by a principal without a second factor |

## SEC-F — Secrets and encryption

| ID | Requirement | Stage | Acceptance |
|---|---|---|---|
| REQ-SEC-046 | `sensitive` fields are encrypted with AES-256-GCM, a data key per tenant, a master key from the environment, **in the stored format specified in [ADR-0019](../adr/0019-sensitive-field-encryption.md)**: a version byte, a `dek_id`, a 12-byte random nonce, the ciphertext and the GCM tag, base64url-encoded, with the two header bytes authenticated. | 1 | `SealedAttributesIT` asserts on the **raw column** that a licence key written through the API is not in it, and `SensitiveFieldCryptoIT` that a stored value parses as that exact layout and that a value whose version byte or `dek_id` is altered fails to decrypt rather than decrypting differently. A `sensitive` field may not also be searchable, sortable or facetable: it would be indexed as ciphertext, and the type editor refuses the combination where it is made |
| REQ-SEC-047 | The encryption uses **additional authenticated data** composed of the two header bytes, `tenantId`, `entityId` and a **length-prefixed** `fieldKey` — unambiguous by construction, so no two different tuples can ever encode to the same AAD ([ADR-0019](../adr/0019-sensitive-field-encryption.md)). | 1 | `SensitiveFieldCryptoIT` moves a ciphertext to another tenant, another entity and another field, and each fails to open. `EnvelopeAadTest` asserts the encoding is injective over the tuple — directly, because through the cipher it could not be observed: two colliding tuples would produce one ciphertext that opened under both |
| REQ-SEC-048 | Tokens are stored in the database only as a hash. | 1 | Verified |
| REQ-SEC-049 | Key rotation is possible without touching the data; the master key supports two active versions, and a tenant's **data** key is versioned by the `dek_id` in each ciphertext, so a new DEK does not require rewriting existing values. A DEK is retired at 2³² encryptions, where the birthday bound on 96-bit random nonces reaches ~2⁻³³ ([ADR-0019](../adr/0019-sensitive-field-encryption.md)). | 1 | `SensitiveFieldCryptoIT` verifies the rotation both ways: a KEK rotation re-wraps without touching ciphertexts — proved against a key the test wrapped itself, from the spec, so the code cannot pass by agreeing with itself — and a DEK rotation leaves old values readable under their own `dek_id`. The operator's procedure is [06 §6.11.1](../architecture/06-deployment-view.md). The per-DEK encryption count is exposed as a metric |
| REQ-SEC-050 | Logs contain no passwords, tokens, keys or `sensitive` values. | 0 | A test with known test values |
| REQ-SEC-051 | `gitleaks` runs in CI and as a pre-commit hook. | 0 | A finding fails the build |
| REQ-SEC-052 | Nextcloud access uses an app password with access to exactly one folder. | 1 | Documented and verified |

| REQ-SEC-101 | **No long-running application service holds the migration credential.** `db-migration-password` is mounted into the one-shot `migrate` service, which uses it, and into `postgres`, which creates the role with it at first initialisation — into nothing else. `api` and `worker` connect only as `homeinv_app` ([ADR-0041](../adr/0041-migration-as-its-own-service.md)). | REQ-SEC-106 | **Signed URLs and pagination cursors have a key of their own**, `HOMEINV_URL_SIGNING_KEY_FILE`, separate from the JWT signing key. `REQ-MED-010` requires short-lived signed media URLs and [08 §8.2](../architecture/08-api-contract.md) an opaque signed cursor; neither named a key. | 0 | A media URL signed with the JWT key is rejected and vice versa; rotating one does not invalidate the other; a tampered cursor is rejected rather than silently returning wrong results |
| REQ-SEC-109 | **The second factor's secret is sealed with a key of its own**, `HOMEINV_CREDENTIAL_KEY_FILE`, mounted as a file and separate from every other key in the deployment. A password is hashed and never recovered; a TOTP secret cannot be, because verifying a code means generating one — so stored as it stands it is a second factor anybody with a database dump can produce, which is the attack a second factor exists for. Not `HOMEINV_URL_SIGNING_KEY_FILE` (`REQ-SEC-106`): rotating the key that signs media URLs must not lock every account out. Recovery codes are **hashed**, not sealed — they are passwords by another name. | 1 | A database dump holds no usable TOTP secret: the stored value opens only with the mounted key, and the application refuses to start without it. | REQ-SEC-107 | **A retention run records where it truncated a tenant's audit chain.** It writes an append-only `audit.chain_truncation` row — oldest retained `seq` and hash, count removed, reason — and marks the affected `chain_anchor` rows `pruned`. Deletions run under `homeinv_housekeeping`, never under the application role ([ADR-0046](../adr/0046-truncatable-audit-chain.md)). | 1 | A retention run over a tenant leaves its chain verifiable and its marker present; removing an entry **without** a marker still reports broken; `homeinv_app` attempting a `DELETE` on `audit` is refused (`REQ-SEC-069`); the anchor chain itself stays unbroken across pruned windows |
| REQ-SEC-102 | **Exactly two containers sit on a non-internal network segment**: `web` and `egress-proxy`. A third fails the build. `frontend` is internal, so adding it changes no count ([ADR-0044](../adr/0044-internal-is-not-a-trust-boundary.md)). Neither of the two holds data, a database credential, an encryption key or domain logic, and the deployment publishes **exactly one** host port ([ADR-0042](../adr/0042-edge-is-not-internal.md)). | 0 | The generated Quadlet units, `compose.yaml` and the Helm chart are read for non-internal segment membership and for published ports; a new member or a second port fails.
