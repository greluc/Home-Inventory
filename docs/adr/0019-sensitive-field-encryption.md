# ADR-0019 — Per-tenant envelope encryption for sensitive fields

**Status:** Accepted · **Date:** 2026-09-11

## Context

Digital items carry licence keys, activation codes and credentials — data that is
directly worth money. The system is reachable from the internet and multi-tenant.
A database dump (a stolen backup, a SQL injection, a compromised database
account) must not expose those values.

## Options

| Option | For | Against |
|---|---|---|
| No encryption | Simple | A dump exposes everything |
| Volume encryption only | Operationally simple | Protects only against physical theft, not against SQL injection and not against a dump taken from the running system |
| **Per-tenant envelope encryption** | Protection even against a database dump; per-tenant key rotation; separation between database access and key access | Encrypted fields are not searchable and not sortable; losing the master key means losing the data |
| End-to-end at the client | The strongest protection | No server-side access, no enrichment, no export by the operator; key management across devices becomes a project of its own |

## Decision

**Envelope encryption**: a data key (DEK) per tenant, wrapped with a master key
(KEK) from the environment
(`HOMEINV_DATA_ENCRYPTION_MASTER_KEY_FILE`). The algorithm is **AES-256-GCM**
with additional authenticated data (AAD) composed of `tenantId`, `entityId` and
`fieldKey`.

Affected are all fields with `sensitive: true` in the type definition, plus
plugin settings of type `secret`.

## Rationale

The AAD is the decisive part: it means an encrypted value **cannot** be moved
into another record, another field or another tenant — decryption fails. Without
AAD, an attacker with write access could copy someone else's secret into a record
of their own and have it displayed.

End-to-end encryption was rejected because it makes export, enrichment and
operator-side recovery impossible — for an inventory system meant to preserve
values over years, that weighs more than the gain.

## The stored format

*Specified 2026-09-11, outstanding item **A9**. The decision above fixed the
algorithm, the AAD composition and two active KEK versions, and left the bytes
undefined — which is the half that cannot be changed after the first value is
written.*

### The field value

A `sensitive` attribute is stored in `item.attributes` (JSONB) as a **base64url
string**, decoding to:

```
 offset  size  field
 ------  ----  --------------------------------------------------------------
      0     1  format version, currently 0x01
      1     1  dek_id — which of this tenant's DEK versions encrypted this value
      2    12  nonce, from a CSPRNG, never reused under one DEK
     14     n  ciphertext (AES-256-GCM)
   14+n    16  GCM authentication tag
```

The two header bytes are **authenticated, not merely present**: they are the
first two bytes of the AAD below. A ciphertext therefore cannot be replayed into
a deployment that reads a later format version, and `dek_id` cannot be flipped to
point at another key.

### The additional authenticated data

```
AAD = version(1) ‖ dek_id(1) ‖ tenantId(16) ‖ entityId(16) ‖ len(fieldKey) u16be ‖ fieldKey(UTF-8)
```

`tenantId` and `entityId` are the raw 16 bytes of the UUID, not its text form.
`fieldKey` is **length-prefixed**, and that is the part worth spelling out: the
AAD must be an *unambiguous* encoding of the tuple. Concatenation alone happens
to be unambiguous today only because the one variable-length member sits last —
so the first time somebody appends a field to this AAD, two different tuples
would start producing the same bytes, and the guarantee this ADR rests on would
be gone with no visible symptom. The length prefix removes that trap now, while
it costs two bytes.

### Keys and rotation

| Point | Value |
|---|---|
| DEK | 256-bit, one per tenant, generated by a CSPRNG |
| KEK | 256-bit, from `HOMEINV_DATA_ENCRYPTION_MASTER_KEY_FILE`; two versions may be active during a rotation |
| DEK wrapping | AES-256-GCM, AAD = `tenantId(16) ‖ kek_version(1)` — so a wrapped DEK cannot be moved to another tenant either |
| Nonce | 12 bytes, random per encryption. **Never** a counter: several `api` instances encrypt concurrently and share no state, so a counter would need coordination that does not exist |
| DEK rotation trigger | At **2³² values encrypted** under one DEK the birthday bound on random 96-bit nonces reaches roughly 2⁻³³, which is where a new DEK version is issued. The count is a metric, not an assumption — the same treatment the public code's redraw rate gets ([ADR-0030](0030-public-code-format.md)) |
| Re-encryption | Issuing a new DEK does **not** rewrite existing values. They keep their `dek_id` and decrypt under the old DEK, which is exactly what that byte is for; a background run re-encrypts them at leisure |

### Where the wrapped DEK lives

`crypto.tenant_data_key`, **its own schema** — for precisely the reason
[07 §7.8](../architecture/07-data-model.md) gives for `idempotency`: several
blocks encrypt (`inventory` for item attributes, `plugins` for settings of type
`secret`), so it belongs to none of them, and it cannot live in `platform`, which
has no schema and no database access at all. Cross-cutting infrastructure, like
`outbox` and `idempotency`.

| Column | Note |
|---|---|
| `tenant_id` | RLS applies; a tenant reads only its own keys |
| `dek_id` | `smallint`, the value stored in the ciphertext header |
| `wrapped_dek` | `bytea`, the DEK under the KEK |
| `kek_version` | which master key version wrapped it |
| `created_at`, `retired_at` | a retired DEK still decrypts; it no longer encrypts |

It carries no `version` and no audit columns: rows are issued and retired, never
edited. It is on the closed **infrastructure** list in
[07 §7.1](../architecture/07-data-model.md), rule 4.

### What this format deliberately does not do

- **No key commitment.** AES-GCM is not committing: a ciphertext can be made to
  decrypt under two different keys. That matters where an attacker chooses keys,
  which is not this threat model — every DEK here is generated by the server and
  never attacker-supplied. It is written down so the omission is a decision and
  not a gap somebody discovers later.
- **No compression before encryption**, ever. Compressing attacker-influenced
  plaintext next to a secret is the CRIME/BREACH shape, and licence keys sit
  beside free-text fields in the same JSONB document.

## Consequences

- **Encrypted fields are not searchable and not sortable.** They are not mirrored
  into `item_attr_index` and not handed to OpenSearch. This is visible in the UI
  when a field is marked `sensitive`.
- Display requires an explicit permission **and** the second factor again; every
  disclosure produces an audit entry.
- In sync, `sensitive` fields are **always** a conflict, never merged
  automatically. The web PWA does not store them locally at all, because
  IndexedDB is unencrypted.
- Key rotation: a tenant's DEK can be re-wrapped without touching the data. The
  KEK supports two active versions for a seamless rotation.
- **A lost master key means permanent loss of those fields.** The key is backed up
  separately from the data backup, in a different place. That sits at the top of
  the operations guide.
- Without a master key set, the application does **not** start. There is no
  generated substitute key.
