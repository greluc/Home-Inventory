| A5 | ~~Verify that port publishing works from an internal network~~ — **measured 2026-09-11, and the assumption was false** ([ADR-0042](0042-edge-is-not-internal.md)). Under Docker a container on an `internal` network gets **no port mapping at all**, and a non-internal network — the only kind that publishes — **always** grants outbound, so "publishes a port" and "has no route out" cannot both hold for one container. The named fallback was taken and verified end to end: `web` becomes the ingress on a non-internal `edge`, `api` publishes nothing. The same trace found that `egress-proxy` sat only on internal segments and could not make the one call it exists for; it gained a non-internal `egress` segment. **Remaining:** the same connectivity suite under rootless Podman with `pasta` and under `kind` — it now verifies a topology known to work rather than one known to work nowhere. | Podman and `kind` runs: with the CI matrix, stage 0 |

| O9 | ~~Push notifications~~ — **decided:** Firebase and APNs, but as a **plugin** and with a **content-free payload** ([ADR-0023](0023-push-notifications.md)). The core keeps its "no outbound route" rule. | — | **done** |
| O10 | ~~Accessibility level~~ — **decided:** WCAG 2.2 AA as the goal, verified automatically (`axe` in CI, keyboard operation, contrast, focus indication), **without** a formal conformance statement. | — | **done** |
| O11 | ~~SMTP egress enforcement~~ — **decided:** the `egress-proxy` gains a plain **TCP forwarding mode** with an exact `host:port` allowlist from the manifest, alongside its HTTP/`CONNECT` mode ([ADR-0027 §3](0027-egress-enforcement.md)). One container, one allowlist source, one access log; STARTTLS and implicit TLS pass through untouched. Rejected: a second forwarder container (two sources, two logs), a minimal MTA (largest attack surface, duplicates the notification block's retry), and an unrestricted segment for `plugin-smtp` (no enforcement for the plugin that carries invitation tokens). | The egress proxy spoke only HTTP, and `plugin-smtp` became stage-1 infrastructure through [ADR-0028](0028-plugin-runtime-stage-1.md) | **done** |
| O12 | ~~UUID in the QR fragment~~ — **decided:** the fragment **stays**, and the fourth reason in [10 §10.1](../architecture/10-identification-and-labels.md) ("information leakage") is **withdrawn**, because it contradicted the very label it was written about. Offline resolution works from *any* label, including one whose binding a device has never synchronised — that is worth more than concealing a creation timestamp. The disclosure is recorded as an accepted risk in [12 §12.3](../architecture/12-security.md) instead of going unmentioned; an operator who disagrees switches the tenant to the host-free code form. | The chapter argued against printing the UUID and then printed it | **done** |
| O13 | ~~Where idempotency records live~~ — **decided:** in **PostgreSQL, in the same transaction as the record they protect** ([ADR-0009](0009-messaging-and-events.md)) — never in a cache. The same argument the outbox rests on: two stores cannot be made consistent by hoping, and here they need not be. Valkey may cache the lookup; it is never the source. | `REQ-API-005` is priority M for mobile clients, and it hung on a store whose loss was documented as harmless | **done** |
| O14 | ~~Relative changes in the sync protocol~~ — **decided:** a change to a numeric field carries `intent: SET \| ADJUST` ([ADR-0014](0014-offline-synchronisation.md)). Deriving deltas unconditionally would have needed no protocol change and was rejected: a stocktake correction concurrent with an offline withdrawal would then count the withdrawal twice — a wrong number arrived at quietly, which is the failure class that chapter exists to prevent. Free now; after the contract is published it would have been a breaking change. | The deltas were derivable from the three-way compare, the **intent** was not | **done** |
| O15 | ~~Is `Cross-Origin-Embedder-Policy: require-corp` worth its cost?~~ — **decided: no, it is removed** ([ADR-0040](0040-no-cross-origin-isolation.md)). It buys cross-origin isolation — `SharedArrayBuffer`, full-resolution timers — and nothing in the design uses either: the ZXing-WASM fallback is single-threaded, local web storage is IndexedDB, and the apps are native. It costs two obligations that fail silently, one of them landing on third-party plugin authors as a blank iframe. `COOP` and `CORP` stay, and CORP stays load-bearing on its own account. The trigger for bringing it back is written into the ADR: the first thing that wants threaded WASM. | Raised and closed in the second review pass of 2026-09-11 | **done** |
| O16 | ~~Where the migration credential lives~~ — **decided:** in a **one-shot `migrate` service**, on all three runtimes, and nowhere else ([ADR-0041](0041-migration-as-its-own-service.md)). Four documents described the migration three different ways and the service matrix described none of them. Running Flyway inside `api` at startup would leave `homeinv_migrator` — the one role that can rewrite an RLS policy — mounted in an internet-facing process for its whole life, which undoes part of what [ADR-0003](0003-multi-tenancy.md) buys. `api` and `worker` now *validate* the schema and refuse to start against an unexpected one. | The corpus said "at startup", "a separate step" and "a `Job`" in different places; `deploy/services.yaml` gave the credential to nobody | **done** |
| O17 | ~~Where the appearance preference lives on the client~~ — **decided:** `localStorage`, as a mirror of the profile value, read by the hash-authorised inline bootstrap before first paint ([ADR-0038](0038-csp-delivery-and-first-paint.md)). A third cookie was drafted first and dropped: it would have ridden every request to pick a colour and needed a `SameSite` decision to be right on the cross-site scan path — the one path [ADR-0029](0029-session-cookie-and-oidc-state.md) exists to protect. The no-flash condition of [ADR-0033](0033-dark-as-default-appearance.md) holds either way; neither beats the first profile load on a new device. | `REQ-NFR-040` required the theme before first paint, the profile is server-side, and the shell is static — three constraints with no stated mechanism | **done** |
