# ADR-0053 — The first owner is created by a one-shot service, not by an endpoint

- **Status:** Accepted
- **Date:** 2026-09-12
- **Deciders:** @greluc
- **Supersedes:** nothing.

It fills a gap [ADR-0028](0028-plugin-runtime-stage-1.md) named and did not close. That
sentence sits below the header rather than on the `Supersedes:` line, because a line that
says "nothing" and then names an ADR reads as a declaration about that ADR — the same
correction ADR-0021 received for the same reason.

## Context

A freshly deployed instance had **no account and no tenant**, and nothing anywhere
could create either. `TenantProvisioningService` existed and was called from tests
and from nothing else; `identity.app_user` was written by tests only. There was no
registration endpoint — deliberately, because stage 0 ships one tenant and an
internet-facing instance that lets strangers create accounts is a different
product — and no invitation, which is stage 1.

So nobody could sign in to a deployed instance. Stage 0's own definition of done,
*"an item can be created, photographed, stored and found again"*, was unreachable
through the product, while every test proved it worked.

[ADR-0028](0028-plugin-runtime-stage-1.md) had already stated the intent in one
sentence — *"its registration path is the operator creating the first account
directly"* — and never said what *directly* is. That sentence is the whole prior
art, and an operator cannot act on it: the password column holds an Argon2id hash,
so "directly" cannot mean SQL typed by hand.

## Options

| Option | Why not |
|---|---|
| **A one-shot `bootstrap` service, like `migrate`** | — chosen |
| A check on `api`'s first start | The most privileged action in the system — creating an owner — would live in the process that serves the internet, and would be evaluated on every start of every replica. `api` also runs as `homeinv_app` for a reason, and this keeps it that way; the objection is about *where* the code sits, not about which credential it uses |
| `setup.sh` creates it | The script would need a way into the database from outside the deployment, or an endpoint that exists only to be called once. The first contradicts [ADR-0022](0022-rootless.md)'s "no bind mounts, no host reach"; the second is a registration endpoint with a different name |
| A documented SQL snippet | Unusable. The operator would have to produce an Argon2id hash by hand with the deployment's own parameters, and a wrong one is an account nobody can sign in to |

## Decision

**The same image runs once more, under a `bootstrap` profile, creates the first
owner and the tenant it owns, and exits.**

It is shaped exactly like `migrate` ([ADR-0041](0041-migration-as-its-own-service.md))
and for the same two reasons:

- **The same image**, because an account created by a different build is an
  account created against different validation, different hashing parameters and
  a different schema.
- **A different process**, because the action is privileged and momentary, and a
  privileged, momentary action does not belong in a long-running service that
  answers the internet.

The inputs follow the rules the rest of the deployment already follows:
`HOMEINV_BOOTSTRAP_EMAIL` is configuration in `compose/.env`, and the password is
a **file** — `HOMEINV_BOOTSTRAP_PASSWORD_FILE`, generated by `setup.sh` into
`deploy/secrets/bootstrap-password` on the first run and never overwritten
(REQ-NFR-054, REQ-NFR-046). With either missing it exits non-zero and `api` does
not start, because an instance nobody can sign in to is not a working instance.

**It is idempotent, and that is load-bearing.** It runs on every deployment of the
stack, not only the first. A second run finds the address taken, creates nothing
and exits 0 — it must not create a second owner, and it must not reset a password
the operator has since changed, which a redeploy would otherwise undo silently.

## Rationale

The alternative that looks cheapest — a check on `api`'s first start — is the one
that spreads. It puts account creation into the request-serving process, where it
is then available to be called from somewhere else later, and it runs on every
start of every replica for the rest of the deployment's life to answer a question
whose answer is "no" every time after the first.

A one-shot answers it once, in its own process, with its own inputs, and leaves
nothing behind. The runtime already understands the shape: Compose gates `api` on
`service_completed_successfully` and Quadlet on a `Type=oneshot` unit that stays
active after exiting — which is also how this ADR found that the generator emitted
neither, for `migrate` either.

## Consequences

- **`deploy/services.yaml` gains a service and a secret**, and the generated
  Quadlet units, `compose.yaml` and the Helm chart follow from it as always.
- **`generate.py` now honours `lifecycle: oneShot`.** It emitted `restart:
  on-failure` and no `Type=oneshot`, so a deterministic failure would have been
  restarted forever under Compose and a Quadlet dependant would have started
  alongside the migration rather than after it. The matrix had claimed both
  behaviours in a comment since it was written.
- **A new module.** `de.greluc.homeinv.bootstrap` depends on `identity.api` and
  `tenancy.api` and publishes nothing. It could not live in either: `identity`
  already depends on `tenancy.api` for the membership lookup during login, so a
  dependency the other way would be a cycle, and Spring Modulith fails the build
  on one.
- **`identity` and `tenancy` each publish one more port.** `UserProvisioning` and
  `TenantProvisioning` — the second is the existing service given an interface, so
  that a caller outside the block reaches it through `api` like every other
  cross-block call (REQ-NFR-021).
- **Stage 1 has somewhere to put invitations.** They call `UserProvisioning` from
  an endpoint; the port does not change.
- **The operator reads the password once.** `setup.sh` prints where it is. Nothing
  displays it again, and rotating it is changing the account's password in the
  application once there is a screen for it — which there is not, at stage 0.
