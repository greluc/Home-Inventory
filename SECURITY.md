## Reporting a vulnerability

**Please do not open a public issue for a security problem.**

Preferred channel — **GitHub private vulnerability reporting**:
<https://github.com/greluc/Home-Inventory/security/advisories/new>

It is encrypted, it keeps the report out of public view, and it gives us a place
to work on a fix and a CVE together without a mailing thread.

If you would rather use e-mail: **lucas.greuloch@gmail.com**.

```bash
# Check the key before you trust it — the fingerprint gpg prints must match
# the one above, character for character.
gpg --show-keys --with-fingerprint SECURITY.asc
gpg --import SECURITY.asc
```

**Verify the fingerprint out of band if you can.** A key published in the same
repository as the claim about it proves only that whoever controls the repository
also controls the key. That is usually enough — but if your report is serious
enough to encrypt, it is serious enough to check against a second source.

If the key is ever rotated or revoked, this file and `SECURITY.asc` are where the
replacement appears.

Reports may be written in German or English.

### What helps

- What you did, what happened, what you expected
- The affected component and, if you know it, the commit or version
- A proof of concept if you have one — even a rough one
- Whether you intend to publish, and when

### What you can expect

| Step | Time |
|---|---|
| Acknowledgement of receipt | within 72 hours |
| Initial assessment (is it a vulnerability, how severe) | within 7 days |
| Coordinated disclosure | **90 days** from the report, or earlier once a fix is available |

We will credit you in the advisory unless you prefer otherwise. If 90 days pass
without a fix, you are free to publish; we would appreciate a heads-up.

## Scope

**In scope** — anything in this repository and anything an operator would deploy
from it:

- Tenant isolation: any way to see or change another tenant's data
- Authentication and authorization: privilege escalation, missing permission
  checks, session handling
- The plugin boundary: a plugin reaching beyond its granted capabilities, or
  escaping its container
- Upload handling: anything that survives re-encoding or the malware scan
- Secrets: exposure of tokens, keys or `sensitive` field values, including in
  logs, error responses or backups
- The deployment descriptions: a configuration we ship that is unsafe by default

**Out of scope**:

- Vulnerabilities in third-party services an operator runs (report those
  upstream), unless our configuration of them is the problem
- Findings that require an operator to have already disabled a documented
  safeguard
- Denial of service through sheer volume against a self-hosted instance
- Reports generated by a scanner with no demonstrated impact

## Design decisions that are security decisions

Some things that look like bugs are deliberate and documented. Please check
before reporting:

| Behaviour | Why |
|---|---|
| A foreign or invisible object returns `404`, not `403` | So the response does not reveal that it exists ([12 §12.5](docs/architecture/12-security.md)) |
| An unknown public code and a code you may not see give the same neutral answer | Same reason ([10 §10.2](docs/architecture/10-identification-and-labels.md)) |
| Uploads are rejected with `503` when the malware scanner is down | Fail-closed is intended ([ADR-0024](docs/adr/0024-malware-scan.md)) |
| In-process plugins are not sandboxed | The JVM cannot sandbox them; that is why they are off by default and operator-only ([ADR-0006](docs/adr/0006-plugin-runtime.md)) |
| The startup aborts when a secret is missing | There is deliberately no generated default key |

If you think one of these decisions is wrong, that is a worthwhile discussion —
open an issue rather than a vulnerability report.

## For operators

When a security release is published it will be announced through GitHub

Watch the repository for security advisories to be notified.
